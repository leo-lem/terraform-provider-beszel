# terraform-provider-beszel

An unofficial, community-maintained Terraform provider for [Beszel](https://beszel.dev), a lightweight
self-hosted server monitoring tool built on PocketBase.

Covers provider lifecycle, CRUD reconciliation against a real REST API, state and import semantics,
acceptance testing, and release tooling.

Not affiliated with or endorsed by the Beszel project.

## Why Beszel

Beszel exposes its data through a standard PocketBase REST API (`/api/collections/{name}/records`)
plus a few custom routes (`/api/beszel/*`). No published Terraform provider exists for it yet, and its
data model is small enough to cover completely while still exercising every interesting provider
concern (relations, JSON blobs, auth-collection quirks, composite identities, singleton resources).

Schema and access rules were reverse-engineered from the Beszel source
(`internal/migrations/`, `internal/hub/collections.go`), not just the docs. See below for what's
authoritative.

## Data model to Terraform surface

Beszel (PocketBase) collections, and how they map:

| Collection | Terraform surface | Why |
|---|---|---|
| `systems` | `beszel_system` resource + data source(s) | User-declared: name/host/port/owners. `info` is agent-written, modeled read-only. |
| `users` | `beszel_user` resource + data source | Auth-collection quirks: write-only password, no read-back. |
| `alerts` | `beszel_alert` resource | Composite natural key (`user`+`system`+`name`), not PocketBase's own `id`. |
| `user_settings` | `beszel_user_settings` resource | Singleton-per-user, upsert semantics, JSON blob (`emails []string`). |
| `alerts_history`, `container_stats`, `system_stats`, `system_details`, `containers`, `systemd_services`, `smart_devices`, `quiet_hours`, `fingerprints` | **not modeled** | Agent-populated telemetry/plumbing. Terraform must never fight the agent for ownership of these. |
| `universal_tokens` | not modeled yet | Goes through a stateful custom route, not plain CRUD. Revisit once the core resources are solid. |

The provider authenticates as a Beszel **superuser** (PocketBase admin). Regular-user auth cannot
create/list `systems` arbitrarily (see `collections.go` rules). This is a real limitation, not an
oversight, and is documented plainly for provider users.

## Project layout

```
.
├── main.go                    # providerserver.Serve entrypoint
├── internal/
│   ├── provider/               # BeszelProvider + one file per resource/data source
│   └── client/                 # hand-written REST client, one file per collection
├── examples/                   # provider + per-resource .tf examples (source for tfplugindocs)
├── docs/                       # generated by tfplugindocs, do not hand-edit
├── .goreleaser.yml             # cross-compile, sign, publish GitHub Release
├── terraform-registry-manifest.json
├── Makefile                    # build, test, testacc, generate, lint
└── .github/workflows/
    ├── test.yml                 # unit + acceptance tests on every PR and push to main
    └── release.yml              # goreleaser release on tag push
```

Client layer: resources never touch raw HTTP/JSON. Each `internal/client/*.go` file exposes typed
`Get/List/Create/Update/Delete` methods per collection, with PocketBase's error envelope mapped to
Go errors (including a typed "not found" so `Read()` can detect out-of-band deletes and call
`RemoveResource`).

## Testing strategy

- **Unit tests** for the client layer against `httptest.Server`, no live Beszel needed, run on every PR.
- **Acceptance tests** (`TF_ACC=1`, `terraform-plugin-testing`) against a real Beszel hub, full
  create/read/update/delete/import cycles per resource. `docker-compose.yml` runs the hub;
  `scripts/testacc-up.sh` provisions it and prints the env vars the tests need:

  ```sh
  eval "$(./scripts/testacc-up.sh)"
  TF_ACC=1 go test ./... -v
  ./scripts/testacc-down.sh
  ```

  The same compose file and scripts are what CI uses to run acceptance tests
  (`.github/workflows/test.yml`).

## Documentation

`docs/` is generated from resource/data source `Description` fields and the `.tf` files under
`examples/`, using `terraform-plugin-docs`. Regenerate after any schema or example change:

```sh
make generate
```

Do not hand-edit files under `docs/`.

## Release process

Releases are cut with GoReleaser (`.goreleaser.yml`): cross-compiles for all supported OS/arch
combinations, produces a checksums file, GPG-signs it, and attaches
`terraform-registry-manifest.json` to the GitHub Release. `.github/workflows/release.yml` runs this
automatically on any `v*` tag push.

This repo has everything prepared for that (manifest, GoReleaser config, release workflow), but the
following one-time steps still need to happen before the first real release, and aren't things this
repo alone can do:

1. Make the repository public (the Terraform Registry only indexes public repos).
2. Generate a GPG key pair; add the public key to the Terraform Registry account under
   Publishing -> Signing Keys.
3. Add `GPG_PRIVATE_KEY` and `PASSPHRASE` as repository secrets in GitHub Actions.
4. Sign in to registry.terraform.io with GitHub and publish this provider (Publish -> Provider),
   pointing it at this repository.
5. Push a `v0.1.0` tag. `release.yml` picks it up, GoReleaser builds and signs the release, and the
   registry ingests the new version automatically within minutes.

Until step 5, `.github/workflows/release.yml` exists but has nothing to trigger it.

## Build order

1. Provider skeleton and auth
2. Client layer for the `systems` collection
3. Core resources and data sources: `beszel_system`, `beszel_user`, `beszel_alert`,
   `beszel_user_settings`, and the read-only `beszel_system(s)`/`beszel_user` data sources
4. Docs generation and release tooling (goreleaser, signed releases, registry publish)
5. CI/CD: unit tests on every PR, acceptance tests against a real Beszel hub, automatic release
   to the Terraform Registry on tag push (current state: workflows in place, registry publish and
   first tag pending the one-time setup above)
